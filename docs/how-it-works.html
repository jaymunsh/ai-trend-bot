Project operating brief

AI 정보를 골라, 한국어로 전달합니다.

27개 출처에서 하루 300건 남짓의 후보를 모아, 편집 기준으로 걸러낸 소수만 원문을 읽고 한국어로 요약해 하루 세 번 전달하는 개인용 자동화입니다.

02

처리 구조

네 단계가 각자의 입출력만 책임집니다. 한 출처가 실패해도 경고만 남기고 나머지는 계속 처리합니다.

03

운영 일정

한국 시간 기준 하루 세 번 실행하고, 회차마다 약 50분 뒤 백업 실행이 한 번 더 걸립니다.

  1. 07:23아침 브리핑 🌅밤사이 올라온 해외 공식 발표와 연구를 반영합니다.
  2. 13:23점심 브리핑 ☀️오전에 추가된 국내외 소식을 보충합니다.
  3. 19:23저녁 브리핑 🌙당일 마지막 업데이트를 전달합니다.

예약 실행은 보장되지 않습니다

GitHub Actions의 schedule은 best-effort 큐입니다. 부하가 높으면 지연되고, 지연이 다음 슬롯까지 밀리면 아예 버려집니다. 30~150분 지연이 흔하고 2026-08-04 13:23 회차는 트리거 자체가 걸리지 않았습니다. 그래서 회차마다 약 50분 뒤 백업 cron을 하나씩 더 둡니다. 백업은 최근 3시간 안에 발송한 기록이 있으면 건너뜁니다. 한 회차를 통째로 놓쳐도 중복 판정이 URL 기준이라 다음 회차가 그대로 후보로 잡습니다. 건수 상한(기본 30, 최대 40)은 목표치가 아니라 폭주 방지선입니다.

05

점수에 임계값을 걸지 않습니다. 모델의 절대 점수는 좁은 구간에 몰려서 어디를 자르든 자의적이 되기 때문입니다. 대신 종류를 매기고, 순위는 후보끼리 비교해 정합니다.

왜 두 번 심사하나

무료 티어 Gemini는 후보 300건대를 한 요청으로 받으면 503을 반환합니다. 그래서 1차는 100건씩 나눠 돕니다. 다만 배치만 나누면 같은 사건을 다룬 두 매체가 서로 다른 배치에 떨어져 둘 다 살아남습니다. 2차는 생존자를 한자리에 놓고 중복을 병합하며, 재심사가 아니라 “오늘 실을 것을 고르는” 선별로 질문을 바꿉니다. 같은 질문을 두 번 하면 이미 통과한 것들이 거의 전부 재승인되기 때문입니다.

텔레그램 한 항목의 형식

01. 제목
[모델·제품 출시]

핵심: 확인된 사실
왜 중요한가: 기술·산업적 의미
관련 대상: 직접 영향을 받는 구체적인 독자

↳ 원문: 매체명

메시지 길이 처리

텔레그램은 4,096자를 넘으면 거부합니다. 3,800자로 자르는 이유는 HTML 이스케이프 때문입니다. 작은따옴표 하나가 &#x27; 6자가 되어 원문 3,900자가 실제로는 4,100자로 전송될 수 있습니다. 쪼개진 메시지에는 헤더 첫 줄 끝에 [1/3]이 붙습니다.

07

Threads 지원 상태

공식 API로는 타인 계정을 수집할 수 없습니다. RSSHub를 경유해 RSS로 받고 있으며, 다른 출처와 동일하게 다룹니다.

공식 API 불가

왜 심사를 통과할 수 없나

타인 공개 계정 조회에는 threads_profile_discovery 권한이 필요합니다. Standard Access로는 @meta, @threads, @instagram, @facebook 네 개만 조회되고, 그 외에는 Meta 앱 심사(2~4주, 실제 서비스의 사용자 플로우 스크린캐스트 제출)를 통과해야 합니다. 개인용 봇은 제출할 사용자 플로우가 없습니다.

RSSHub 경유

현재 방식

rsshub.rssforever.com/threads/choi.openai를 RSS로 읽습니다. 토큰도, 60일 갱신도, 심사도 필요 없습니다. 대신 공용 인스턴스라 자주 타임아웃되며, 실패하면 그날 이 출처만 빠지고 브리핑은 정상 발송됩니다.

남아 있는 코드

ai_trend_bot/threads.py는 본인 계정 조회를 위해 남겨두었습니다. 이 경로는 threads_basic만으로 동작하지만 현재 파이프라인에서는 호출하지 않습니다. 안정성이 필요해지면 RSSHub를 직접 띄우는 것이 다음 선택지입니다.

08

운영과 점검 방법

브리핑이 마음에 안 들면 코드가 아니라 config/editorial.md를 고칩니다. 한국어 산문으로 쓰인 편집 방침이 그대로 선별 프롬프트에 들어갑니다.

기준을 고친 뒤 확인

uv sync
uv run ai-trend-bot check-config
uv run ai-trend-bot run --dry-run

실제 텔레그램 발송

uv run ai-trend-bot run --send

드라이런은 무엇이 왜 걸러졌는지 사유와 함께 보여줍니다 (--show-dropped, 기본 켜짐). 기준이 느슨하다고 느끼면 편집 방침의 “반드시 걸러낼 것”에 항목을 추가하고, 중요한 걸 놓치면 “반드시 통과시킬 것”에 추가합니다.

09

제약과 다음 단계

개인용 무료 운영에는 충분하지만, 외부 서비스의 정책·형식·할당량에 영향을 받습니다.

발송량이 회차마다 흔들림

실측 7건 · 14건 · 30건. 2차를 선별로 프레이밍해 최악(상한 도달)은 잡았지만 LLM 판단이라 편차가 남습니다. 계속 많으면 편집 방침을 조입니다.

Gemini 요청 크기 한계

무료 티어는 후보 300건대를 한 요청으로 받으면 503을 반환합니다. 100건씩 배치로 나눠 우회하고 있으며, 일시적 5xx·429는 5초 → 20초 → 60초로 재시도합니다.

RSSHub 공용 인스턴스 불안정

Threads 수집이 자주 타임아웃됩니다. 실패해도 그 출처만 빠집니다. 안정성이 필요하면 직접 띄우는 것이 해법입니다.

Anthropic · Meta AI 커버리지 공백

두 회사는 RSS를 제공하지 않아 직접 수집이 불가능합니다. 소식이 테크 미디어 경유로만 들어와 하루 정도 늦을 수 있습니다.

예약 실행이 몇 분 늦을 수 있음

GitHub Actions cron은 정확한 실시간 스케줄러가 아닙니다. 5~15분 지연은 정상 동작입니다.

다음으로 해볼 개선

편집 방침 실사용 튜닝, 실패 알림, 주간 회고 브리핑, 90일 초과 기록 정리 순으로 확장하면 운영 가치가 큽니다.

현재 결론

추가 서버 없이 무료 한도 안에서 돌고 있습니다. 남은 과제는 기능이 아니라 편집 기준의 튜닝입니다. 며칠 받아보며 config/editorial.md를 조정하는 것이 가장 효과가 큽니다.

이 문서는 저장소의 실제 설정과 구현을 기준으로 작성되었습니다.
설계 배경과 결정 근거는 docs/superpowers/specs/의 설계 문서에 있습니다.
