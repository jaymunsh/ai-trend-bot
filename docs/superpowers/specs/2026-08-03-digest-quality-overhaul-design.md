# AI 트렌드 봇 — 브리핑 품질 개편 설계

작성일: 2026-08-03
상태: 2~4단계까지 구현 완료 (2026-08-03). 구현 중 확정된 사실은 아래 '구현 결과'에 기록.

## 1. 배경

현재 봇은 RSS 8개 소스에서 모은 항목을 Gemini로 요약해 하루 3회 15개씩 발송한다. 운영해 본 결과 세 가지 문제가 확인되었다.

1. **안 중요한 게 섞인다.** 튜토리얼·홍보성 글이 실제 뉴스와 같은 비중으로 온다.
2. **요약이 얕다.** 읽어도 무엇이 새로운지, 왜 중요한지 알기 어렵다.
3. **중요한 걸 놓친다.** 다른 경로로 먼저 접한 큰 소식이 브리핑에 없거나 늦게 온다.

### 1.1 원인

세 증상은 서로 다른 문제가 아니라 두 가지 구조적 원인에서 나온다.

**원인 A — 판단하는 층이 없다.** 파이프라인은 "아직 안 본 것 = 보낼 것"으로 동작한다. Gemini가 `relevance` 0~100을 매기지만, 프롬프트가 이를 "참고값일 뿐"이라고 명시하고 실제로 어디에도 쓰지 않는다. 대신 `select_balanced_items`가 출처별 라운드로빈으로 15칸을 **채운다**. 좋은 항목이 3개뿐인 날에도 12개를 끌어온다. 잡음의 직접적 원인이다.

**원인 B — 요약본을 다시 요약한다.** `feeds.py`가 Gemini에 넘기는 본문은 RSS의 `summary` 필드뿐이다. OpenAI 블로그 등 다수 피드는 두세 문장짜리 티저만 제공한다. 원문을 읽지 않았으므로 깊이가 나올 수 없다. 15개 전부를 요약하는 현재 구조에서는 본문 fetch 비용을 감당할 수 없어 이 제약이 고정되어 있다.

세 번째 증상(누락)은 소스가 벤더 공식 블로그 + arXiv뿐이라는 커버리지 문제이며, 원인 A가 해결되지 않으면 소스를 늘릴 수 없다는 점에서 A에 종속된다.

### 1.2 Threads 관련 조사 결과

`threads.py`는 `@choi.openai` 같은 관심 계정을 수집하도록 구현되어 있으나 현재 비활성 상태다. 조사 결과 **이 경로는 사실상 실현 불가능**하다.

- 타인 공개 계정 조회에는 `threads_profile_discovery` 권한이 필요하다.
- Standard Access에서는 `@meta`, `@threads`, `@instagram`, `@facebook` 네 개 공식 계정만 조회된다.
- Advanced Access는 Meta 앱 심사(2~4주, 실제 서비스의 사용자 플로우 스크린캐스트 제출)를 요구한다. 개인용 봇에는 제출할 사용자 플로우가 없다.
- 장기 토큰 60일 만료는 `refresh_access_token`(`grant_type=th_refresh_token`, 발급 24시간 후 ~ 60일 이내 호출)으로 갱신 가능하나, 위 권한 문제가 선결 조건이므로 무의미하다.

따라서 **공식 API 대신 RSSHub `/threads/:user` 라우트를 경유**한다. 토큰·심사가 불필요하고 RSS로 수신한다. 공용 인스턴스는 레이트리밋으로 간헐 실패하나, 소스별 실패 격리 구조가 이를 흡수한다.

`threads.py`의 본인 계정 조회 경로는 `threads_basic`만으로 동작하므로 향후 확장을 위해 남긴다.

## 2. 목표와 비목표

### 목표

- 발송되는 항목이 **선별된 결과**가 되도록 판단 층을 신설한다.
- 요약이 **원문 본문**에 기반하도록 한다.
- 커버리지를 8개 → 30개 안팎 소스로 넓히되, 잡음이 늘지 않도록 한다.
- 같은 사건의 중복(매체 간 중복, 후속 보도)을 제거한다.
- 발송 기록이 유실되지 않도록 한다.
- 선별 기준을 코드가 아닌 **편집 가능한 파일**로 분리하고, 왜 걸러졌는지 확인 가능하게 한다.

### 비목표

- 웹 UI, 대시보드는 만들지 않는다.
- 다중 사용자·구독자 개념은 도입하지 않는다. 개인용 봇을 유지한다.
- 유료 API·유료 인프라를 도입하지 않는다. 무료 티어 내에서 운영한다.
- Meta 앱 심사는 추진하지 않는다.

## 3. 확정된 운영 기준

| 항목 | 내용 |
| --- | --- |
| 발송 시각 | 07:30 / 13:30 / 19:30 (Asia/Seoul) |
| 발송 개수 | **가변.** 기준 통과분만 발송. 0건이면 발송하지 않음 |
| 안전 상한 | 회당 40건 (목표치가 아닌 폭주 방지선). 초과 시 순위 하위를 잘라내고 잘린 건수를 로그에 남긴다 |
| 중복 정책 | URL 재발송 금지, 매체 간 사건 병합, 후속 보도 제외 |
| 기록 보관 | 저장소 커밋 (`data/sent.jsonl`) |
| 비용 | 무료 티어 내 운영 |

cron은 UTC 기준으로 `30 22 * * *`, `30 4 * * *`, `30 10 * * *`이다. GitHub Actions 예약 실행은 부하에 따라 5~15분 지연되는 것이 정상이며, 정시 도착은 보장되지 않는다.

## 4. 전체 구조

현재는 `pipeline.run()` 하나가 수집·중복제거·선별·요약·발송을 모두 수행한다. 소스 30개와 2단 판단을 얹으면 유지 불가능하다. 네 단계로 분리한다.

```
① 수집   collect/     각 소스 → RawItem[]           소스별 어댑터, 실패는 격리
                              ↓  300~400건
② 선별   triage/      RawItem[] → Verdict[]         신설. 품질의 대부분이 여기서 결정
                              ↓  통과분만 (보통 3~15건)
③ 심화   enrich/      원문 본문 fetch → 깊은 요약    통과분에만 적용
                              ↓
④ 전달   deliver/     렌더링 → 텔레그램 → 기록 커밋
```

### 분리 근거

**② 독립 모듈화는 테스트를 위한 것이다.** 현재 선별 로직을 검증하려면 파이프라인 전체를 목킹해야 한다. `RawItem[] → Verdict[]`라는 순수 함수 경계가 생기면 실제 기사 픽스처를 넣고 결과를 직접 검증할 수 있다. 기준을 반복 튜닝하려면 이 경계가 필수다.

**③ 분리는 비용을 위한 것이다.** 본문 fetch와 심층 요약은 ②를 통과한 소수에게만 적용한다.

전체 원칙은 **"싸게 넓게 거르고, 비싸게 좁게 판다"**이다.

## 5. ① 수집 계층

### 어댑터 인터페이스

모든 소스는 `fetch() → tuple[RawItem, ...]` 하나의 인터페이스를 구현한다. 소스 종류별 어댑터는 셋이다.

| 어댑터 | 대상 | 비고 |
| --- | --- | --- |
| RSS | 대부분의 소스 | 현재 `FeedClient` 확장 |
| Hacker News | HN Algolia API | 점수 임계값과 AI 키워드 필터 필요 |
| Hugging Face | HF 트렌딩 모델 API | 신규 오픈웨이트 모델 포착 |

RSSHub 경유 Threads는 RSS 어댑터를 쓰되, 실패 빈도가 높으므로 warning 처리만 하고 재시도하지 않는다.

소스 목록은 `config/sources.toml`에서 계속 관리한다. 종류(`kind`) 필드가 추가된다. **소스 추가가 TOML 몇 줄로 끝나야 한다.**

### 소스 구성 (약 30개)

| 계층 | 내용 |
| --- | --- |
| 벤더 공식 | 현행 6개 + Anthropic, Meta AI, Mistral, Microsoft, Apple 등 |
| 벤더 changelog | OpenAI / Anthropic / Google AI API 변경 로그 |
| 테크 미디어 | TechCrunch AI, VentureBeat AI, Ars Technica |
| 커뮤니티 | Hacker News(고득점), r/LocalLLaMA, GitHub 트렌딩 |
| 큐레이터·뉴스레터 | Simon Willison, Import AI, The Batch |
| 연구 | arXiv cs.AI (현행), Hugging Face 트렌딩 |
| 국내 | 네이버·카카오·LG·삼성 AI 발표, 국내 규제·정책 |
| Threads | `@choi.openai` (RSSHub 경유) |

**구체적 피드 URL은 구현 시 각각 실제 응답을 확인한 뒤 확정한다.** 위 목록은 커버리지 의도를 정의한 것이며, RSS를 제공하지 않는 곳은 대체 경로를 찾거나 제외한다.

## 6. ② 선별 계층 — 핵심

Gemini 호출 **한 번**이 네 가지를 동시에 수행한다.

### 6.1 분류

각 항목에 종류를 부여한다.

| 분류 | 처리 |
| --- | --- |
| 모델·제품 출시 | 통과 후보 |
| 연구 결과 | 통과 후보 |
| 정책·산업·자금 | 통과 후보 |
| 도구·오픈소스 | 통과 후보 |
| 튜토리얼·사용법 | 기본 제외 |
| 홍보·사례소개 | 기본 제외 |
| 기타 | 기본 제외 |

**점수 임계값을 쓰지 않는 이유:** LLM의 절대 점수는 보정되지 않아 대부분 70~85 구간에 몰린다. 임계값을 어디에 두든 절단이 자의적이 된다. 반면 "이것이 어느 칸인가"는 훨씬 안정적으로 재현된다. "AWS Bedrock으로 챗봇 만들기"가 제외되는 것은 점수가 낮아서가 아니라 **분류가 다르기** 때문이다.

### 6.2 사건 병합

같은 사건을 다룬 항목들을 하나로 묶는다. 대표 항목 하나를 선정하고 나머지는 참고 링크로 첨부한다. 소스가 30개가 되면 이 처리 없이는 브리핑이 같은 사건으로 도배된다.

### 6.3 후속 판정

최근 2주치 발송 기록의 **사건 요지 목록**을 입력에 함께 넣어, 이미 다룬 사건의 재탕·후속인지 판단한다. URL이 다르므로 해시 기반 중복 제거로는 잡히지 않는다. 현재 SQLite에는 해시만 저장되어 이 판단이 불가능하며, 이것이 저장 형식을 바꾸는 이유 중 하나다.

### 6.4 순위

남은 항목들을 **상대 비교**로 정렬한다. 절대 점수가 아니라 "이 중 무엇이 더 중요한가"를 묻는다. LLM은 절대 평가보다 상대 평가에서 일관성이 높다.

### 6.5 기준 파일

선별 기준은 `config/editorial.md`에 한국어 산문으로 작성한다. 코드가 아닌 **편집 방침 문서**다.

초안은 사용자가 밝힌 네 가지 용도를 반영한다.

- 내가 쓸 도구·기술 찾기
- 업계 흐름 따라가기
- 콘텐츠·글감 소재
- 놓치면 안 되는 것

프롬프트에 문자열로 박지 않는 이유는 명확하다. **기준은 반복적으로 틀리고, 틀렸을 때 고칠 수 있어야 기준이다.** 코드 수정 없이 이 파일만 편집하고 드라이런으로 확인하는 흐름이 되어야 한다.

### 6.6 출력

항목마다 `분류 / 통과여부 / 사유 / 병합된 사건 / 순위`를 반환한다. **탈락 항목도 사유와 함께 반환한다.** 드라이런에서 "무엇이 왜 잘렸는지"를 볼 수 없으면 기준을 튜닝할 수 없다.

## 7. ③ 심화 계층

1단 통과분에 한해 원문 HTML을 받아 본문을 추출한 뒤 심층 요약한다.

- **본문 추출:** `trafilatura`. 광고·내비게이션을 제거하고 본문만 추출한다.
- **폴백:** 추출 실패 시 RSS 요약을 사용한다. 페이월·JS 렌더링 사이트는 추출되지 않으며, 이 경우 **해당 항목만 얕아지고 브리핑은 정상 발송된다.** 실행이 중단되어서는 안 된다.
- **요약 형식:** 현행 `핵심 / 왜 중요한가 / 관련 대상` 3줄 구조를 유지한다. 재료가 티저에서 본문으로 바뀌므로 같은 형식에서도 밀도가 올라간다.

## 8. ④ 전달 계층

### 8.1 브리핑 형식

`parse_mode="HTML"`로 전환한다 (텔레그램은 표·제목 태그를 지원하지 않으므로 굵게·인용·하이퍼링크만 사용). 링크 미리보기는 현행대로 비활성화한다.

확정된 형식 (2026-08-03, 실제 발송으로 검증):

```
🌅  AI 트렌드 브리핑 · 아침 07:30        ← "AI 트렌드 브리핑"만 굵게
8월 3일 (월) · 3건

────────────────

01. 앤스로픽, 자동화 에이전트 'Cowork' 출시   ← 줄 전체 굵게
[모델·제품 출시]

핵심: Claude Desktop에서 파일을 직접 다루는 에이전트를 공개했습니다.
왜 중요한가: 작업 범위가 채팅창 밖으로 넓어집니다.
관련 대상: Claude Desktop 사용자

↳ 원문: VentureBeat AI                    ← 매체명에 기사 링크

────────────────

02. 오픈소스 AI 코드 에디터 'Void' 프로젝트 중단
[도구·오픈소스]
...
↳ 원문: Hacker News (AI) · TechCrunch     ← 병합 시 링크 여러 개
```

| 위치 | 내용 |
| --- | --- |
| 헤더 1줄 | 🌅/☀️/🌙 + AI 트렌드 브리핑 + 회차·시각 |
| 헤더 2줄 | 월·일 (요일) · N건 |
| 항목 1줄 | `01. 제목` (굵게) |
| 항목 2줄 | `[카테고리]` |
| 본문 | 핵심 / 왜 중요한가 / 관련 대상 |
| 마지막 | `↳ 원문: 매체명` |

- 상단 이모지는 회차별로 바뀐다: 아침 🌅 / 점심 ☀️ / 저녁 🌙. 장식이자 회차 식별자다.
- **"원문:"을 글자로 쓴다.** 매체명만 파랗게 있으면 그것이 출처 표기인지 누를 수 있는
  링크인지 읽히지 않는다. 실제 발송 후 사용자가 "링크가 어디 있느냐"고 되물은 데서
  확인된 문제다. raw URL 노출은 한 줄을 다 잡아먹고 병합 시 여러 줄이 되므로 쓰지 않는다.
- 건수를 헤더에 표시해 가변 발송임을 드러낸다.
- 3,800자를 넘으면 메시지가 쪼개지고, 쪼개진 메시지마다 헤더가 다시 붙는다.

### 8.2 저장

두 종류를 서로 다른 곳에 저장한다.

**발송 기록 — `data/sent.jsonl`, 저장소 커밋**

매 실행 후 append하고 커밋·푸시한다. 한 줄의 내용:

| 필드 | 용도 |
| --- | --- |
| URL 해시 | 재발송 차단 |
| 제목 | 사람이 읽기 위함 |
| **사건 요지 (한 줄)** | **후속 판정의 입력** |
| 분류 | 통계·튜닝 |
| 발송 시각 | 회차 추적 |
| 병합된 출처 목록 | 디버깅 |

저장소 커밋을 선택한 근거는 아래와 같다. 세 후보 모두 무료이므로 기준은 비용이 아니라 **소실 위험**이다.

| 방식 | 판단 |
| --- | --- |
| GitHub Actions 캐시 (현행) | 7일 미사용·용량 초과 시 evict. 유실이 정상 동작이며, 유실 시 수십 건 대량 재발송 |
| Turso 등 외부 DB | 무료 플랜 조건이 변경될 수 있고 미사용 DB 정지 조건이 붙는다. 계정·토큰 관리 부담 추가 |
| **저장소 커밋 (선택)** | GitHub이 저장소를 유지하는 한 소실되지 않는다. 별도 시크릿 불필요 (`GITHUB_TOKEN` + `contents: write`). git 이력이 기준 튜닝의 근거로 남는다 |

용량은 연 2MB 수준이다. 90일 초과분은 잘라낸다. 워크플로에 `concurrency` 그룹이 있어 동시 실행 충돌은 없다.

**선별 전체 기록 (탈락분 포함) — Actions artifact**

매 실행 400건이 쌓이므로 커밋하지 않는다. 무료 500MB, 자동 만료라 관리가 불필요하다. 기준이 이상하게 동작할 때만 해당 실행의 artifact를 내려받아 확인한다. 로컬 드라이런에서는 터미널에 출력한다.

### 8.3 발송과 기록의 원자성

현재는 텔레그램 청크를 순차 발송한 뒤 전체를 한 번에 기록한다. 중간 청크에서 실패하면 일부만 발송된 채 기록이 남지 않아, 다음 실행이 전체를 재발송한다.

**청크 단위로 성공한 만큼만 기록**하도록 변경한다.

## 10. 테스트

현재 테스트는 함수 단위라 "브리핑이 실제로 좋아졌는가"를 검증하지 못한다.

- **선별 통합 테스트:** 실제 기사 20~30건을 픽스처로 고정하고 1단 선별을 통째로 실행해 결과를 검증한다. 기준 파일을 수정할 때마다 실행해 회귀를 잡는다. LLM 출력은 완전 결정론적이지 않으므로 **"이 항목은 반드시 탈락 / 이 항목은 반드시 통과"** 수준의 느슨한 단언을 사용한다.
- **렌더링 스냅샷:** 가변 건수(0건, 1건, 40건), 병합 다중 출처, 긴 제목 등 경계 조건.
- **저장 왕복:** `sent.jsonl` 기록 → 재로드 → 후속 판정 입력 생성.
- 기존 단위 테스트는 유지하되 삭제되는 기능의 테스트는 함께 제거한다.

## 11. 제거되는 것

| 대상 | 사유 |
| --- | --- |
| `select_balanced_items` | 라운드로빈 칸 채우기. 잡음의 직접 원인 |
| `run_limits`, `daily_max`, `sum == daily_max` 검증 | 개수 제한 폐지 |
| CLI `--limit` (현재 max=20) | 동일 |
| SQLite `SeenStore` | `data/sent.jsonl`로 이관 |
| Threads `profile_posts` 경로 | 심사 없이 동작 불가. 본인 계정 조회 경로는 존치 |

기존 SQLite의 해시는 `sent.jsonl`로 이관한다. 사건 요지가 없으므로 해시만 옮기며, 이관분은 후속 판정에 기여하지 않고 재발송 차단에만 쓰인다.

## 12. 자원 예산

**GitHub Actions** — 비공개 저장소 Free 플랜 월 2,000 Linux 분. 1회 실행은 수집(병렬) + Gemini 2회 + 본문 10건 fetch + 발송·커밋으로 2~3분. 하루 3회 = 9분, **월 약 270분 (한도의 14%)**.

**Gemini API** — 무료 티어 flash-lite 기준 하루 1,000~1,500 요청. 회차당 2~3콜(1단 1회, 2단 1~2 배치)이므로 **하루 6~9콜 (한도의 1% 미만)**. 분당 토큰 25만 제한 대비 1단 입력이 약 2.5만 토큰으로 여유가 크다. 컨텍스트 100만 토큰이므로 400건 일괄 입력에 문제가 없다.

**본문 fetch** — 하루 30건 남짓의 HTTP GET.

실질적 제약은 API 한도가 아니라 RSSHub 공용 인스턴스의 안정성이다.

## 14. 작업 순서

한 번에 전환하지 않는다. 각 단계마다 실제 브리핑을 받아 확인한 뒤 다음으로 진행한다.

**1단계 — 기반 정리**
기록 저장소 이전(커밋 방식), 스케줄 변경(07:30/13:30/19:30), 브리핑 형식 개편, 발송·기록 원자성 수정. 선별 품질은 현행 그대로 두고, **소실되지 않는 기록부터** 확보한다.

**2단계 — 선별 계층 신설**
`triage/` 모듈, `editorial.md`, 분류·병합·후속·순위, 개수 제한 제거, 탈락 사유 출력. **여기서 잡음이 사라진다.**

**3단계 — 심화 계층**
`trafilatura` 본문 추출, 2단 심층 요약, 폴백 처리. **여기서 요약이 깊어진다.**

**4단계 — 소스 확대**
30개 소스로 확대, 어댑터 3종 구현, 피드 URL 검증.

**4단계를 마지막에 두는 것이 중요하다.** 거르는 층 없이 소스를 먼저 늘리면 브리핑이 쓰레기통이 된다.

이 설계는 네 단계 전체를 다루지만, **구현 계획은 단계별로 따로 작성한다.** 한 계획에 넣기에는 범위가 넓고, 각 단계의 실사용 결과가 다음 단계의 입력이 되기 때문이다. 특히 2단계 완료 후 `editorial.md` 조정 기간이 필요하며, 그 결과가 3·4단계의 세부를 바꿀 수 있다.

## 15. 성공 판정

- 조용한 날에 3~5건, 사건이 많은 날에 15건 이상이 오며, 두 경우 모두 자연스럽게 읽힌다.
- 튜토리얼·홍보성 항목이 브리핑에서 사라진다.
- 요약만 읽고도 무엇이 새로운지 판단할 수 있어, 원문을 열지 않고 넘어가는 항목이 생긴다.
- 같은 사건이 여러 항목으로 중복 등장하지 않는다.
- 기준이 어긋났을 때 `editorial.md` 편집과 드라이런만으로 교정된다.

### 설계와 달라진 점

**LLM 호출 타임아웃.** 후보 300건대를 한 번에 심사시키면 응답이 수만 토큰이라 클라이언트
기본값 30초로는 부족하다. Gemini 호출에만 300초를 건다. 전역으로 올리면 느린 피드까지
같이 기다리게 되므로 호출 지점에만 적용했다.

**소스별 항목 상한(`max_items`).** arXiv cs.LG는 한 번에 247건을 반환한다. 소스마다
상한을 두지 않으면 한 소스가 후보 풀을 독점한다. 설계에 없던 필드다.

**Threads 파이프라인 분기 삭제.** 공식 API 경로가 실현 불가능하므로 `pipeline.py`에서
Threads 분기를 제거했다 (`enabled = false`라 이미 죽은 코드였다). `threads.py` 모듈은
본인 계정 조회를 위해 남겼으나 현재 호출되지 않는다.

**본문 추출을 워커 스레드에 넘기지 않는다.** 대상이 수십 건 규모라 이벤트 루프에서
직접 호출한다. `enrich.py`에 `ponytail:` 주석으로 표시했다.

**선별 전체 기록을 Actions artifact로 올리지 않는다.** 드라이런 터미널 출력
(`--show-dropped`)으로 충분하다. 필요해지면 그때 추가한다.

**선별을 2회로 나눈다 — 설계에서 가장 크게 달라진 부분.** 설계는 Gemini 호출 한 번이
분류·병합·후속판정·순위를 모두 처리한다고 봤다. 실제로는 무료 티어가 후보 322건짜리
요청에 503(high demand)을 반환한다. 재시도로는 풀리지 않는다. 같은 키로 작은 요청은
200이고, 200건까지는 통과하므로 크기 문제다.

그래서:

1. **1차** — 후보를 100건씩 배치로 나눠 병렬 심사
2. **2차** — 1차 생존자(수십 건)를 한 번에 놓고 다시 심사

2차가 필요한 이유는, 배치만 나누면 같은 사건을 다룬 두 매체가 서로 다른 배치에 떨어져
둘 다 살아남기 때문이다. 후보가 우선순위 내림차순으로 정렬돼 있어 공식 발표(80)와
테크 미디어(20)는 거의 항상 다른 배치에 들어간다. 즉 배치 단독으로는 병합이 사실상
동작하지 않는다.

`gemini.triage()`를 그대로 두 번 호출하는 구조라 새로 만든 코드는 `_triage()` 한 메서드뿐이다.

**Gemini 재시도.** 5초 → 20초 → 60초. 일시적 429/5xx가 회차 전체를 날리는 것을 막는다.
transport의 `retries=3`은 연결 실패만 처리하고 HTTP 상태코드는 재시도하지 않는다.

## 17. 프롬프트 전문

LLM 호출은 세 곳이다. 두 개는 코드에 있고(`ai_trend_bot/gemini.py`), 하나는 편집 가능한

### 17.1 선별 프롬프트 — `GeminiClient.triage()`

편집 방침 전문과 최근 2주간 보낸 사건 목록을 함께 주입한다. 구조화 출력은
`VerdictBatch`의 JSON Schema로 강제한다.

```
당신은 AI 소식 브리핑의 편집자입니다. 아래 편집 방침에 따라 후보를 심사하세요.

=== 편집 방침 ===
{config/editorial.md 전문}

=== 최근 2주간 이미 보낸 사건 ===
{sent.jsonl에서 읽은 event 목록, 없으면 "(없음)"}

각 후보에 대해 다음을 판정하세요.
- category: 항목의 종류.
- event: 이 항목이 다루는 사건을 한 문장으로. 같은 사건이면 같은 표현을 쓰세요.
- duplicate_of: 앞선 후보와 같은 사건을 다루면 그 index. 아니면 null. 가장 원본에
  가깝고 정보가 많은 쪽을 대표로 남기세요.
- keep: 편집 방침에 비추어 보낼 가치가 있으면 true. 위 '이미 보낸 사건'의 재탕이나
  후속 보도면 false.
- reason: 판정 이유를 한 문장으로. 탈락시킨 경우 특히 구체적으로.
- rank: 중요한 순서대로 1부터. 서로 비교해서 매기세요.

{2차 라운드에서만: 최종 선별 지시문, 17.2 참조}
모든 입력 항목을 빠짐없이 반환하고 입력의 index를 그대로 유지하세요. JSON만 반환하세요.
입력: [{"index": 0, "title": "...", "source": "...", "excerpt": "본문 앞 400자"}, ...]
```

설계 의도:

| 지시 | 의도 |
| --- | --- |
| `category` | 0~100 점수를 대체한다. 모델의 절대 점수는 좁은 구간에 몰려 임계값이 자의적이 된다. "어느 칸인가"는 훨씬 안정적으로 재현된다 |
| `event` | 사건 요지. 발송 후 `sent.jsonl`에 저장되어 다음 회차의 후속 판정 입력이 된다. URL이 달라도 재탕을 잡는 유일한 수단 |
| `duplicate_of` | 그룹 구조를 출력시키는 대신 대표 index 하나만 지목하게 한다. 모델이 동일한 그룹 ID 문자열을 일관되게 만들어내지 못하기 때문 |
| `reason` | 탈락 사유. 기준을 튜닝하려면 왜 걸렸는지 보여야 한다 |
| `rank` | 절대 점수가 아니라 상대 비교. 모델은 "이 중 뭐가 더 중요한가"에 훨씬 일관적이다 |
| `excerpt` 400자 | 1차는 싸야 한다. 후보 300건대에 본문 전체를 넣을 수 없다 |

`category`가 `튜토리얼·사용법` / `홍보·사례소개` / `기타`면 `keep` 값과 무관하게
코드에서 버린다(`triage.DROPPED_CATEGORIES`). 모델이 관대해도 분류는 뒤집히지 않는다.

### 17.2 최종 선별 지시문 — `pipeline.FINAL_ROUND_GUIDANCE`

2차 라운드에만 추가로 붙는다.

```
이것은 최종 선별입니다. 위 후보는 이미 1차를 통과한 것들이므로 개별적으로는 모두
그럴듯해 보입니다. 지금 할 일은 재심사가 아니라 **오늘 브리핑에 실을 것을 고르는
것**입니다. 하루 세 번 발송하므로 한 회차에 실리는 것은 보통 3~8건입니다. 서로
비교했을 때 상대적으로 약한 것, 같은 회사의 사소한 업데이트, 같은 사건의 다른 측면을
다룬 것은 keep=false로 떨어뜨리세요. 애매하면 버립니다.
```

이 문단이 없으면 2차가 1차와 같은 질문("이 항목이 보낼 가치가 있나")을 반복하고,
이미 통과한 것들은 개별로 보면 모두 그럴듯하므로 거의 전부 재승인된다. 실제로 이
문단을 넣기 전 예약 실행이 상한 30건을 채웠다. 넣은 뒤 같은 후보 풀에서 14건.

### 17.3 요약 프롬프트 — `GeminiClient.summarize()`

선별을 통과한 소수에만 적용한다. `content`는 `trafilatura`로 추출한 기사 원문이며,
추출 실패 시 RSS 티저로 폴백된다.

```
다음 AI 관련 항목을 한국어로 번역·요약하세요. 입력 content는 기사 원문입니다.
제목만 바꿔 쓰지 말고 원문에서 구체적인 사실을 끌어내세요. summary는 '핵심:',
'왜 중요한가:', '관련 대상:' 세 줄로 구성하세요. 핵심에는 제품명·수치·기능 등 확인된
사실을 1~2문장으로, 왜 중요한가에는 기존 방식과 달라진 점이나 기술·산업적 의미를 한
문장으로 쓰세요. 관련 대상에는 이 소식의 영향을 직접 받는 연구자·개발자·제품팀·
의사결정자 중 가장 구체적인 독자를 적으세요. '활용하세요', '검토하세요'처럼 근거 없는
일반론은 쓰지 마세요. '획기적', '비약적', '대폭' 같은 과장 표현을 쓰지 말고 입력에
없는 성과나 전망을 추측하지 마세요. 제목은 간결하게 작성하세요. 모든 입력 항목을
빠짐없이 반환하고 입력의 index를 그대로 유지한 뒤 JSON만 반환하세요.
입력: [{"index": 0, "title": "...", "content": "원문 본문", "source": "..."}, ...]
```

설계 의도:

- **"입력 content는 기사 원문입니다. 제목만 바꿔 쓰지 말고"** — 개편 전에는 RSS 티저를
  넣었기 때문에 모델이 제목을 다시 쓰는 것 외에 할 수 있는 일이 없었다. 재료가 바뀌었음을
  명시해야 실제로 본문을 파고든다.
- **3줄 고정 구조** — 자유 형식은 항목마다 길이와 초점이 달라져 훑어보기 어렵다.
- **"관련 대상"에 가장 구체적인 독자** — 이것이 없으면 "AI 개발자" 같은 무의미한 답이
  나온다.
- **"활용하세요", "검토하세요" 금지** — 근거 없는 행동 권유는 요약을 길게만 만든다.
- **"획기적", "비약적", "대폭" 금지 + 입력에 없는 전망 추측 금지** — 보도자료 톤과
  환각을 동시에 막는다.
- **index 유지** — 반환 순서가 아니라 index로 원본과 대응시킨다. 개수가 맞지 않으면
  `SummaryMismatchError`로 실패시킨다. 조용히 어긋난 요약을 붙이는 것보다 낫다.
