# 편집 방침

이 파일이 무엇을 보낼지 정하는 기준입니다. 브리핑이 마음에 안 들면 코드가 아니라
이 파일을 고치고 `--dry-run`으로 확인하세요.

## 독자

AI를 실제로 만들고 쓰는 한 사람. 이 브리핑을 네 가지 용도로 읽습니다.

1. **내가 쓸 도구·기술 찾기** — 새 모델, 라이브러리, API 변경 중 당장 적용할 만한 것
2. **업계 흐름 따라가기** — 누가 무엇을 내놓고 판이 어떻게 움직이는지
3. **콘텐츠·글감 소재** — 남들이 아직 모를 만한 것, 이야기가 되는 것
4. **놓치면 안 되는 것** — 큰 발표는 반드시

## 반드시 통과시킬 것

- 새 모델·제품의 공개, 가격 변경, 성능·컨텍스트·비용 등 사양이 실제로 바뀐 발표
- API·SDK의 파괴적 변경, deprecate 공지, 새 기능
- 주목할 만한 오픈웨이트 모델 공개
- 기존 통념을 뒤집거나 실무 판단을 바꾸는 연구 결과
- 규제·소송·대형 투자·인수처럼 업계 구조에 영향을 주는 사건
- 사고, 장애, 보안 문제, 회수

## 반드시 걸러낼 것

- **"X로 Y 만들기" 형태의 튜토리얼·하우투.** 새 소식이 아니라 사용법입니다.
  특히 클라우드 벤더 블로그에 많습니다.
- **고객 사례·도입 후기·파트너십 홍보.** 누가 무엇을 도입했다는 사실만으로는 부족합니다.
- 이미 알려진 내용의 재정리, 요약 기사, 리스티클
- 제품 이름만 바뀐 리브랜딩, 사소한 버전 표기 변경
- 채용, 행사 안내, 웨비나 모집
- 구체적 결과 없이 전망·의견만 담은 글

## 판단이 애매할 때

- **새로운 사실이 있는가?** 없으면 버립니다. 읽고 나서 "그래서 뭐가 달라졌지"라는
  답이 안 나오면 통과시키지 마세요.
- 같은 사건을 여러 곳이 다뤘다면 **원본에 가깝고 정보가 많은 쪽**을 남깁니다.
  회사 공식 발표 > 1차 보도 > 요약 기사 순입니다.
- 연구 논문은 결과가 구체적이고 검증 가능할 때만 통과시킵니다.
  arXiv에는 하루에도 수백 편이 올라오므로 기본은 탈락입니다.
- Hacker News 항목은 점수·댓글 수가 높다는 이유만으로는 부족합니다.
  내용 자체가 위 기준을 넘어야 합니다.
- 애매하면 **버립니다.** 조용한 브리핑이 잡음 섞인 브리핑보다 낫습니다.

## 순위

위 네 가지 용도에 얼마나 직접 닿는지로 매깁니다. 큰 회사가 냈다는 이유만으로
위로 올리지 마세요. 작은 팀의 오픈웨이트 모델이 대기업의 소소한 업데이트보다
위일 수 있습니다.
